# Фильмоскоп — курсовая Sprint 2

RAG по базе поддержки. Код разложен по `pipeline/`, тяжёлые прогоны — скриптами, в ноутбуке в основном разбор результатов.

## Запуск

```powershell
cd Sprint2\Project

# LLM на 8080 (LM Studio + proxy или свой сервер)
python run_stages_1_4.py   # чистка, чанки, chroma, rerank
python run_stages_5_6.py   # генерация + судья (~20 мин на 66 запросах)
```

На GPU с ~16 GB VRAM retrieve на этапах 5–6 лучше на CPU:

```bash
FILMOSKOP_RETRIEVE_DEVICE=cpu python run_stages_5_6.py
```

Результаты — в `artifacts/` (`verdict.json`, копия зачётного прогона в `artifacts/t4_run/`).

## С чем столкнулись

**Грязный корпус.** В разделах смесь HTML/markdown и кракозябр (UTF-8, прочитанный как latin-1). Без нормализации кодировки и снятия разметки поиск ломался на очевидных вопросах. Короткий мусор отрезали, разделы с восстановимым текстом оставили.

**Чанкинг режет смысл.** Fixed window с overlap давал хуже recall: фразы рвались посередине. Sentence window (~500) с title в начале чанка оказался стабильнее на multi-запросах.

**Dense top-5 не дотягивал.** Baseline recall@5 был около 0.66: нужный раздел часто уже был в top-20, но не в top-5. Просто увеличить K недостаточно — нужен реранкер.

**Hybrid почти не помог.** BM25 + RRF на этом корпусе дал почти нулевой прирост относительно dense. В финал не пошёл; оставили сравнение в артефактах.

**Реранкер тяжёлый по VRAM/latency.** Связка dense top-20 → bge-reranker-v2-m3 → top-5 закрыла порог recall ≥ 0.85, но на одной карте с LLM приходится экономить память.

**7B не влезает вместе с retrieve.** На T4 (~16 GB) модель ~7B конфликтует по VRAM с эмбеддером/реранкером. Для генерации и судьи взяли ~3B; на этапах 5–6 retrieve уводили на CPU (`FILMOSKOP_RETRIEVE_DEVICE=cpu`).

**Gap и формулировки ответов.** Модель то дописывала факты вне базы, то отказывала «криво», и судья штрафовал correctness. Помогли жёсткий промпт («только по фрагментам»), нормализация отказа и на gap — отказ, если ответ слабо опирается на фрагменты.

**Сломанный LLM-судья (замечание ревью).** На 3B модель часто эхом повторяла шкалу «от 1 до 5», а парсер брал первую цифру → relevance≈1 при верных ответах. Исправлено: отдельный короткий вызов судьи, очистка эха шкалы, повтор при подозрительно низкой оценке; лексический fallback для correctness только как страховка парафраза.

**Аномалия золотого контекста.** Раньше в gold подставляли целые разделы (длиннее top-5 чанков) → correctness gold < final. Теперь gold = чанки `relevant_docs` в том же формате, что RAG; gold ≥ final.

**Парсинг судьи.** Маленькая модель часто отвечает не «5», а текстом вроде «цифра от 1 до 5». Старый `re.search([1-5])` брал первую единицу — из‑за этого faithfulness/relevance «сыпались» при нормальных ответах. Теперь берём оценку из `Оценка: N` / последнюю изолированную цифру; золотой контекст сравниваем с финалом в `verdict.json`.
